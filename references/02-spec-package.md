# 02 方案包：把对话冻成 12 份文档

P2 的产物是 `02_方案/` 下 12 份 Markdown。**不是写给人看的报告，是写给「下一轮的你」和用户看的施工图。** 判据只有一条：隔一天换个会话，只读这 12 份就能接着写代码，不用回头问用户。

```

```

## 01_决策追踪.md（先写这份）

一张表，每个需要拍板的问题一行。**冻结的含义 = 这张表没有「待定」行。**

```markdown
| 编号 | 问题 | 选项 | 决定 | 理由 | 日期 | 可否更改 |
|---|---|---|---|---|---|---|
| D-01 | 技术路线 | 零构建 / TS+Vite | 零构建 | 单屏玩法，无构建更快交付 | 2026-11-20 | 否 |
| D-02 | 音频 | 文件 / 合成 / 无 | Web Audio 合成 | 上传包无音频白名单 | 2026-11-20 | 否 |
| D-03 | 海报 | 要 / 不要 | 要，3:4，1080×1440 | 传播主路径 | 2026-11-20 | 是 |
```

规矩：
- 「可否更改=否」的项，后面任何阶段都不能单方面改，要改必须用户点头并写变更记录。
- 编号在代码注释和阶段报告里引用（`// 见 D-04`），方便回溯。
- 有 `UNKNOWN` 的地方单独在 `12_风险与未知.md` 编号（U-01…），决策表里写「依赖 U-03」。

## 02_PRD.md

最少包含：

1. **一句话介绍**（给用户看的，将来能直接当简介草稿）
2. **目标用户与场景**：谁、在哪、为什么玩 30 秒
3. **核心循环**：进入 → 操作 → 反馈 → 结算 → 再来一局，每步一句话
4. **V1 范围**：必做清单（可验收的动宾短语，不写「优化体验」这种）
5. **非目标**：这版明确不做什么（防止范围膨胀）
6. **成功标准**：能过审 + 单局完整 + 无崩溃，三条写死

## 04_玩法规则.md

这份要写到「照着能写代码」的粒度：

1. **状态机**：状态列表 + 转移条件（`ready → playing → paused → result → ready`），每个转移写触发事件。
2. **输入**：支持的输入类型、判定区域、是否允许多点、滑动阈值（像素或屏幕比例）。
3. **核心判定**：命中/失败的具体条件（用坐标、时间窗口、重叠面积描述，不写「感觉」）。
4. **数值表**：所有常量集中成一张表（速度、间隔、生命、分数权重、难度档位）。带单位。
5. **随机性**：用不用随机、种子从哪来、能否复现一局（`seed` 可传给测试）。
6. **结算**：分数公式、评级分档、最高分更新规则。
7. **边界情况**：屏幕最窄/最宽、快速连点、切后台再回来、中途旋转、连续失败 20 次。
8. **与表现分离**：写清哪些是纯逻辑（可单测）、哪些是渲染。

## 05_界面与文案.md

1. **屏幕清单**：按顺序列（启动/首页 → 玩法 → 暂停 → 结算 → 设置），每屏一张 ASCII 线框或布局说明。
2. **每屏元素**：元素名、位置、字号、颜色、触控尺寸（**≥44×44 CSS px**）。
3. **全部中文文案**：按钮、标题、提示、错误、空态。**一次写全，别边写代码边编。**
4. **安全区**：顶部留 `statusBarHeight`，底部留 `safeArea.bottom` 对应高度，写清用 CSS 变量兜底。
5. **状态覆盖**：加载中、无存档、存档损坏、能力不可用、权限被拒 各自显示什么。

## 06_视觉与素材.md

- 画布基准：390×844 CSS px（宽度自适应，高度自适应）。
- 色板：主色/辅色/背景/文字/危险，给十六进制。
- 字体：只用系统字体栈（不打包字体文件，除非确实要 woff2 子集且有许可）。
- 素材清单表：`文件名 | 用途 | 尺寸 | 来源（自绘/生成/AI） | 许可`。
- **许可是硬要求**：AI 生成的写工具名和日期；素材站的要授权类型；不能确认来源的一律自己重做。

## 07_音频方案.md

- 音效清单：`事件 | 音色描述 | 时长 | 合成参数（频率/波形/包络）`。
- **不允许**把 mp3/wav/ogg/m4a 放进上传包（文档白名单里没有音频扩展名）。
- 路线优先级：① Web Audio 程序化合成（推荐，零文件）② 音频字节编码进外置 JS 运行时解码（体积大、未验证，需实测）③ 纯静音（必须在交付说明里写明，不许说「音频已完成」）。
- 必须写：首次用户手势解锁 AudioContext、切后台暂停、静音开关持久化、合成失败时游戏照常可玩。

## 08_平台能力.md

一张表，覆盖用到的每个 `window.xhs.miniTool` 方法：

| 能力 | 方法 | 最低版本 | 能力检测 | 失败表现 | 降级 |
|---|---|---|---|---|---|
| 存储 | setStorage/getStorage | 9.46+ | `typeof mt.setStorage === 'function'` | 返回 false | 仅内存，界面提示「本机不保存」 |
| 安全区 | getWindowInfo | 9.49+ | 同上 | 抛错 | 用 CSS env() 兜底 |
| 关注 | followAuthor | 9.51+ | 两个方法都要有 | errCode 20002/15404/10003 | 隐藏入口，不显示失败 |
| 分享 | share | 9.53+ | 存在 + 全屏 | 抛错 | 退回 postNote |
| 发笔记 | postNote | — | 存在 | 唤起失败 | 只 toast，文案写「没能打开编辑器」 |

再写三条调用约定：

1. 三层判空 `window.xhs → .miniTool → .方法`，全部包 `try/catch`。
2. **按方法存在判断能力，不按版本号猜**（真机可能读不到版本）。
3. 平台不可用时，游戏必须完整可玩，只是入口不显示。

## 09_技术架构.md

- 目录树（`src/` 下每个文件一句话职责）。
- 模块边界：`platform`（平台桥接）/ `audio` / `game-core`（纯逻辑）/ `render` / `ui` / `main`。
- 数据模型：存档结构（key 名、版本号、字段、迁移策略、容量上限 1MB/key）。
- 构建方式：零构建（源码即产物）或 `npm run build`（target ES2017、IIFE、外置 JS）。
- 单条红色底线：**最终 HTML 里不许有内联 `<script>`、行内 `on*`、`javascript:`。**

## 10_测试矩阵.md

按四类列用例，每条写「操作 → 期望」：

1. **功能**：核心玩法的判定、计分、重开（覆盖正常 + 边界）。
2. **兼容**：窄屏 320、长屏 430×932、Chrome 61 语法、无 SDK、旧版本能力。
3. **异常**：存储失败、能力抛错、用户取消、连续快速点击、切后台。
4. **性能**：首屏可见时间、低端机帧率目标（60 目标 / 30 可接受）、包体积。

每条用例标注执行环境：`浏览器 / 模拟器 / 真机`，**报告里必须分开写，不能合并成「PASS」**。

## 11_阶段计划.md

P3–P7 每阶段写：目标、进入条件、任务清单（动宾短语）、验证项、证据路径、退出条件。详见 `03-build-gates.md`。

## 12_风险与未知.md

| 编号 | 类型 | 描述 | 影响 | 缓解 | 状态 |
|---|---|---|---|---|---|
| U-01 | 未知 | 原版连击阈值未确认 | 手感可能不同 | 先用 5，等用户试玩反馈 | OPEN |
| R-01 | 风险 | 上传包可能拒收某类资源 | 上线阻塞 | 只用自绘 + 合成音频 | 已缓解 |

**每个 UNKNOWN 都要写「怎么才能确认」**（问用户 / 实测 / 看文档），否则它会一直挂着。

## 冻结怎么做

1. 12 份写完，自查一遍「出口条件」。
2. 给用户一段**不超过 12 行**的摘要 + 3 个必须他拍板的点，让他回一句「方案没问题」。
3. 用户确认后，在 `01_决策追踪.md` 顶部写：

```
> 冻结时间：<日期>　冻结版本：V1.0　确认人：<用户>
```

4. 之后任何改动只能通过 `变更记录.md`：

```markdown
| 日期 | 变更 | 原因 | 影响文档 | 影响代码 | 已回归 |
|---|---|---|---|---|---|
```

**没冻结不许进 P3 写正式代码。** 最多写探针/原型验证可行性（并注明是探针）。

## 常见漏项自查

- [ ] 有没有「胜利」条件？还是只有失败结束？
- [ ] 首次进入有没有 3 秒内的操作提示？
- [ ] 结算页放哪几个按钮，顺序是什么？
- [ ] 切后台回来，游戏是暂停还是继续？计时器怎么办？
- [ ] 存档损坏/版本升级，读不出来怎么办？
- [ ] 用户连续点 10 次开始按钮会怎样？
- [ ] 有没有哪句话会让用户以为「发布成功了」而其实没有？
